# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. `README.md` covers the human-facing quick start/usage/parameter reference — this file focuses on things a human README wouldn't (internal architecture, non-obvious bugs and their fixes, why things are built the way they are).

## What this is

A Nextflow DSL2 pipeline (single `main.nf`) that takes paired-end Illumina reads from Atrandi combinatorial-barcoded SAG libraries through to decontaminated, annotated assemblies: Atrandi demultiplexing (Pheniqs) → QC → trimming → complexity filtering → k-mer normalization → host/contaminant read removal (BWA) → assembly (SPAdes) → contig trimming/dedup → host/contaminant contig removal (BLAST) → CheckM completeness → Prokka annotation → SSU (16S) recovery + classification → GTDB-Tk taxonomy → viral classification → a single per-sample stats table. It is the archival pipeline for the paper "Single-particle genomics uncovers abundant non-canonical marine viruses from nanolitre volumes" — changes should preserve fidelity to what produced the paper's results (hence e.g. GTDB-Tk pinned at 2.0.0 / GTDB r207), not silently modernise tool versions.

## Running the pipeline

```bash
nextflow run main.nf                       # normal run, reads from ./input/, writes to ./results/
nextflow run main.nf --dev                 # dev mode: only carries params.dev_num_capsules capsules into assembly (default 3; CH_fastq.take(params.dev_num_capsules), applied post-demux — every pool is still demultiplexed in full)
nextflow run main.nf --dev --dev_num_capsules 5   # same, but carry 5 capsules instead of the default 3
nextflow run main.nf --indir <dir> --output <dir>
nextflow run main.nf -stub-run --dev       # fast DAG/wiring smoke test — see "Stub-run support" below
```

There is no test suite or linter — `-stub-run` (see below) is the closest thing to one.

`nextflow.config` is gitignored (see `.gitignore`) — it does not exist in a fresh clone and must be created locally before running. It currently sets:
```groovy
process.container = 'quay.io/nextflow/bash'
docker { enabled = true; autoMounts = true }
```
Docker must be running locally; all processes execute inside per-process containers.

Nextflow itself lives in the `nextflow-env` conda environment (`/opt/anaconda3/envs/nextflow-env`), not on the base PATH — activate that env before running `nextflow` directly.

### Input naming convention

Files in `params.indir` must be paired FASTQ named `<library>_R1.fastq.gz` / `<library>_R2.fastq.gz` (`.fastq`/`.fq`/`.fq.gz` also matched). The workflow derives the library ID by stripping `_R1`/`_R2` from the filename and pairs mates via `groupTuple(size:2)` — mismatched or unpaired files will break grouping. Each pair is an Atrandi pool, not a single SAG — see "Atrandi demultiplexing" below for how it becomes one `(ID, r1, r2)` tuple per capsule.

## Pipeline architecture

One process per stage in `main.nf`, wired together in the `workflow {}` block. Tool versions are pinned via container tags (some also encoded in the process name, e.g. `_v0_11_9`, though a few processes have drifted from their name — check the actual `container` line, not just the process name).

### Atrandi demultiplexing

Atrandi's combinatorial barcoding multiplexes many single-cell capsules into one Illumina pool via 4 independent 8bp barcode positions (D, C, B, A) embedded in the first 44bp of R2, at fixed offsets `D=0:8, C=12:20, B=24:32, A=36:44` (4bp linker gaps between windows; linker content itself isn't read by the demux). This subworkflow runs first, ahead of every existing read-processing stage, and turns each input pool into one `(ID, r1, r2)` tuple per capsule — `ID` = `<library>_<capsuleID>` — so nothing downstream of `TRIM_BARCODE` needed to change.

Two-pass design, both passes via Pheniqs (`pheniqs mux`):
1. **Frequency estimation** (cheap, on a subsample): `SAMPLE_READS` (`seqtk sample`, `params.sample_num_reads` reads) → `PHENIQS_MAKE_SAMPLE_CONFIG` (builds a Pheniqs config with 4 *independent* barcode-caller rounds, one per D/C/B/A list in `params.barcode_dir`) → `PHENIQS_SAMPLE_DEMULTIPLEX` → `PHENIQS_COUNT_SORT_SAMPLE` (tallies reads per observed `D-C-B-A` combo from the BAM's `CB` tag) → `PHENIQS_PLOT_HIST` (QC histogram vs. `params.read_threshold`) → `PHENIQS_FILTER_BC_LIST` (keeps combos with count ≥ `params.read_threshold`, i.e. real capsules vs. noise, capped at `params.cell_threshold`).
2. **Real demultiplex** (on the full pool): `PHENIQS_NAME_CAPSULES` assigns each accepted combo a capsule ID (e.g. `19140024`, the concatenated D/C/B/A list indices) and builds a *single*, `knit`-ed Pheniqs config against it → `PHENIQS_DEMULTIPLEX` runs that against the full R1/R2, emitting one fastq pair per capsule (named `<library>_<capsuleID>_r{1,2}.fastq.gz`) plus an `undetermined` bucket for everything else → `PHENIQS_PARSE_REPORT` turns Pheniqs' own JSON report into a CSV.

The workflow block regroups `PHENIQS_DEMULTIPLEX.out.list_fastq` into `(ID, r1, r2)` tuples and filters out `undetermined` before anything else runs. `TRIM_BARCODE` (`trim_galore --clip_R2 params.barcode_trim_length`) then strips the barcode+linker bases Pheniqs leaves at the front of R2 — without it, that structural sequence would flow straight into `FASTQC_v0_11_9`/`TRIMMOMATIC_v0_32` as if it were genomic content.

**`params.dev` semantics**: applied *after* demux, not before — every pool is always demultiplexed in full; `--dev` only caps how many resulting capsules get carried into assembly, via `CH_fastq.take(params.dev_num_capsules)` (`params.dev_num_capsules` defaults to `3`, independently configurable rather than a bare hardcoded `take(1)`). Demux itself is cheap relative to assembly, so there's no benefit to skipping it in dev mode, and skipping it would leave dev-mode runs untested against the actual barcode-matching logic. Under `--dev` only, `CH_fastq` is sorted by ID (`toSortedList { a, b -> a[0] <=> b[0] }.flatMap { it }`) before `.take()`, so repeated dev runs pick the *same* capsules rather than whatever order `PHENIQS_DEMULTIPLEX`'s output glob happens to list them in — Nextflow doesn't document process output globs as sorted, and capsule ID order isn't meaningful anyway (it's just concatenated D/C/B/A barcode-list indices, unrelated to read count/quality), so this is about reproducibility, not picking "the best" capsules. The sort is skipped entirely on normal (non-`--dev`) runs, since `toSortedList()` has to collect the whole channel into memory before re-emitting — fine for a handful of dev capsules, but would otherwise force every capsule through demux before any of them could start assembly on a real production run.

**Containers**: the old pipeline this was ported from (a separate, HPC-flavored repo) pointed at Galaxy's Singularity depot (`depot.galaxyproject.org/singularity/...`). Every one of those tags is directly Docker-pullable from `quay.io/biocontainers/` under the identical tag (confirmed via the Quay API — the Singularity depot mirrors these same images), so no substitution was needed for Pheniqs itself. `PHENIQS_MAKE_SAMPLE_CONFIG`/`PHENIQS_FILTER_BC_LIST`/`PHENIQS_NAME_CAPSULES`/`PHENIQS_PARSE_REPORT` all reuse `quay.io/biocontainers/pandas:2.2.1` (already pinned here for `ASSEMBLY_STATS_TABULATOR`) rather than adding a separate bare-Python image for the two of those scripts that only need the stdlib. `PHENIQS_COUNT_SORT_SAMPLE` reuses the `samtools:1.24` pin already used by `CONTAM_READ_REPORTER`, rather than the older `1.17` the source pipeline used.

**`PHENIQS_DEMULTIPLEX` OOM'd against real data**, root-caused to Pheniqs' own buffering, not the pool size: Pheniqs defaults to buffering 2048 records *per feed* (input or output — [confirmed against Pheniqs' own `configuration.json`](https://github.com/biosails/pheniqs/blob/master/configuration.json), not guessed), and this process opens one output feed pair per surviving capsule. A real pool with ~1900 capsules surviving `params.read_threshold` means ~3800 simultaneously-buffered output feeds — roughly 2000x the buffering footprint a single-output process would have, and the actual dominant cost, not pool size or thread count (`task.cpus` isn't set anywhere in this pipeline, so Pheniqs already runs single-threaded here). Fixed with `params.pheniqs_buffer_capacity` (default `64`, passed as `-B`) rather than by chasing the memory ceiling upward — a non-data-discarding fix, unlike raising `read_threshold`/lowering `cell_threshold`, which was also considered but rejected here since the observed count distribution was gradual rather than cleanly bimodal, so there was no obvious noise-floor cutoff to raise it to without risking real capsules. `memory`/`errorStrategy` on this process were being hand-tuned directly against the live machine while root-causing this — check the process itself for current values rather than assuming a fixed retry ladder is still in place.

**Only `SAMPLE_READS` and `PHENIQS_DEMULTIPLEX` of these 10 processes have a `stub:` block** — the other 8 follow the same precedent as `FASTQC_v0_11_9`/`TRIMMOMATIC_v0_32`/`COMPLEXITY_FILTER` below (see "Stub-run support"): `stub:` here is reserved for steps that are genuinely slow, and Pheniqs `mux` (on the frequency-estimation subsample) plus the awk/pandas/trim_galore helpers are fast enough on both tiny CI data and real runs to just execute for real under `-stub-run`. Both exceptions share the same root cause: **`--dev`'s `CH_fastq.take(params.dev_num_capsules)` only trims capsules *after* the whole pool has already been processed**, so neither `seqtk sample` (`SAMPLE_READS`) nor `pheniqs mux` on the full, un-subsampled pool (`PHENIQS_DEMULTIPLEX`) gets any faster under `--dev` — both stay slow against a real multi-GB fastq even in `-stub-run --dev`. `SAMPLE_READS`'s stub grabs a real prefix of R2 (`zcat | head`, fast because `head` closes the pipe early); `PHENIQS_DEMULTIPLEX`'s stub fakes `params.dev_num_capsules` capsule pairs the same way, plus a minimal-but-structurally-valid report JSON (a single dummy barcode/count/index row) so `PHENIQS_PARSE_REPORT` right after it doesn't choke on an empty one. Both hand **real** slices of data downstream rather than placeholders, since the non-stubbed processes right after each of them (`PHENIQS_SAMPLE_DEMULTIPLEX`, `TRIM_BARCODE`) need genuinely shaped input. This also means CI's `-stub-run` exercises the actual barcode-matching logic on the frequency-estimation pass (via `.github/test_data/generate_atrandi_test_data.py`'s synthetic reads), not just a placeholder — the real demux itself just isn't re-run per-capsule under stub-run.

**Not wired into the stepwise-count/`assembly_stats.csv` system** (see "Stepwise count logging" below) — that system's numbering (`1_raw` … `9_checkm`) is tightly coupled to `ASSEMBLY_STATS_TABULATOR`'s fixed `LIST_col_order`; inserting a pre-demux stage would mean renumbering it. Demux QC artifacts (configs, the observed-barcode histogram, the Pheniqs report) instead publish to `results/sample_tracking/atrandi_demux/<library>/`, outside that combined table.

**Read processing:** `FASTQC_v0_11_9` → `TRIMMOMATIC_v0_32` → `COMPLEXITY_FILTER` (drops low-complexity pairs, `templates/complexity_filter.py`) → `KMERNORM_v1_0_0` (k-mer normalization) → `DEINTERLEAVE` (bbmap `reformat.sh`, splits the interleaved normalized file back into separate `r1_norm_<ID>`/`r2_norm_<ID>` files). Per-sample readcounts (`Raw_readcount`, `Trimmed_readcount`, etc.) sum both mates (r1 + r2), not just r1.

**Read decontamination:** `CONTAM_READ_FINDER` (`bwa aln`/`bwa sampe` against `params.contam_ref_fasta`) → `CONTAM_READ_REPORTER` (`samtools view -F0x0004`, keeps only reads that actually aligned to the contaminant reference) → `CONTAM_READ_REMOVER` (`templates/contam_read_remover.py`, drops any read pair whose name appears in the reporter's hit list from the *pre-alignment* interleaved `normalized_pe_<ID>.fastq.gz`).

**Assembly:** `SPADES_v3_15_2` (`--sc --careful`, single-cell mode) → `TRIM_CONTIGS` (`templates/trim_and_deduplicate_contigs.py`: length-filters by `params.assembly_minlength`, trims `params.assembly_lefttrim`/`assembly_righttrim` bp off each end, and drops contigs that are exact reverse-complement duplicates of another contig — a known SPAdes v3 artifact that gets contigs rejected by NCBI/GenBank).

**Contig decontamination:** `CONTAM_CONTIG_FINDER` (`blastn` of trimmed contigs against `params.contam_ref_fasta`, using `params.contam_min_length`/`contam_min_percid` as the relevant thresholds) → `CONTAM_CONTIG_REMOVER` (`templates/contam_contig_remover.py`, publishes the final `SCGC_<ID>_contigs.fasta`). Both now run on `TRIM_CONTIGS.out.trimmed_contigs` — `CONTAM_CONTIG_REMOVER` used to be joined against `length_passing_contigs` (2a, *not* end-trimmed), which both (a) meant its excision coordinates were computed from a different fasta than the BLAST hits `CONTAM_CONTIG_FINDER` produced, and (b) left `SCGC_<ID>_contigs.fasta` un-end-trimmed. Fixed to `trimmed_contigs` on both sides (matches `pilot_boothbay_capsules`), so `SCGC_<ID>_contigs.fasta` is genuinely trimmed **and** decontaminated.

**`CH_final_contigs` — the one downstream channel.** `CONTAM_CONTIG_REMOVER.out.contigs.filter({ it[1].size()>0 })`, defined in the workflow block right after the count `collectFile`. Every stage below consumes this: `MEASURE_SAG`, `CHECKM_v1_1_9`, `PROKKA_v1_14_6`, `PROKKA_GFF_2_TSV`, the SSU block, `GTDBTK_v2_0_0`, and the whole viral block. Previously these ran off `TRIM_CONTIGS.out.trimmed_contigs` (pre-contig-decontamination) while the `SCGC_<ID>_contigs.fasta` output went nowhere — annotating the decontaminated assembly is the point of the 2026-09 annotation port.

**Stats:** `MEASURE_SAG` (max contig length, total assembly length, GC%) and `CHECKM_v1_1_9` (`checkm lineage_wf --reduced_tree`, genome completeness) run in parallel off `CH_final_contigs`, then `ASSEMBLY_STATS_TABULATOR` pivots every stage's counts into one wide `assembly_stats.csv` (one row per sample) — see "Stepwise count logging" below.

### Annotation: Prokka, SSU (16S), GTDB-Tk

Ported from `BigelowLab/pilot_boothbay_capsules` in 2026-09. All run off `CH_final_contigs`.

- **`PROKKA_v1_14_6` → `PROKKA_GFF_2_TSV`** — Prokka with `--proteins params.prokka` (SwissProt), genetic code from `CH_translation_table` (pulled out of CheckM's `bin_stats.analyze.tsv` in Groovy). `PROKKA_GFF_2_TSV` (`templates/prokka_gff_2_tsv.py`) writes the comprehensive per-CDS TSV and a `prokka_stats_<ID>.csv` countfile (`CDS`, `tRNA`, `percent_CDS_annotated`, `average_CDS_length`, `coding_density`) — that countfile is now wired into the stepwise-count system (`10_prokka_stats.csv`); it previously went nowhere.
- **SSU recovery + classification** — `SSU_BLAST` (`blastn -task megablast` of the assembly vs `params.silva_blastdb`) → `SSU_GET_GENE` (pysam `faidx`/`fetch` pulls the best-hit region out of its contig; runs in the `pysam` image, *not* a `samtools` CLI image) → `SSU_CLASSIFIER` (`templates/ssu_classifier.py`, CREST-style LCA against `params.silva_map`/`params.silva_tree`, biopython image) → `PARSE_CLASSIFIER` (top-3 recovered SSU classifications → `11_ssu_classification.csv`). `ssu_classifier.py` is the pilot script with the `six` Py2/3 shim removed, `Counter` imported (pilot used it un-imported in `BlastHits.majority()`), and an empty-input guard so a capsule with no SSU hit writes empty outputs instead of trying to load the SILVA tree.
- **`GTDBTK_v2_0_0` → `PARSE_GTDBTK`** — `gtdbtk classify_wf` (pinned 2.0.0 / GTDB **r207**, `params.gtdb` → `GTDBTK_DATA_PATH`), gated on `countBases(it[1]) > params.gtdbtk_min_bp` (2500). `PARSE_GTDBTK` records `classification_via_GTDBTk` + `multicopy_marker_genes` → `12_gtdbtk_stats.csv`. **`memory '128 GB'` / `cpus 8` is hardcoded for charlie (PBS)** — `classify_wf`'s pplacer step is the driver; tune for other environments. This is the one new process whose real `script:` block cannot run under `-stub-run` in CI (needs the ~66GB DB) and is also skipped there anyway because the stub assembly is <2500 bp — its `stub:` fakes the two summary TSVs `PARSE_GTDBTK` reads.
- New `assembly_stats.csv` columns: `CDS`, `tRNA`, `percent_CDS_annotated`, `average_CDS_length`, `coding_density`, `1/2/3_SSU_classification`, `classification_via_GTDBTk`, `multicopy_marker_genes`. `ASSEMBLY_STATS_TABULATOR` now `.reindex(columns=LIST_col_order)` instead of `[LIST_col_order]`, so a metric no sample produced this run (every assembly below `gtdbtk_min_bp`, or no SSU recovered) comes through as an empty column instead of `KeyError`.
- **Reference DBs (`params.silva_*`, `params.gtdb`, `params.prokka`) are user-supplied, not auto-downloaded** — unlike the contaminant reference. See README "Annotation / classification databases". TODO in `ANNOTATION_PORT_ROADMAP.md` (gitignored, on charlie): publish SILVA + SwissProt to Zenodo and switch to the BWA_INDEX-style bootstrap.

### Viral classification (geNomad, VirSorter2, CheckV, DeepVirFinder, ViralRecall2)

Gated by `params.viral` (default `true`), this block runs on `CH_final_contigs` (the fully decontaminated + trimmed assembly — see above; it used to run off `TRIM_CONTIGS.out.trimmed_contigs`), restricted for `GENOMAD_v1_11_1` specifically to capsules whose longest contig exceeds 1500bp (`maxContigLength()`, defined just above the `workflow {}` block). The `CH_FINAL_CONTIGS` alias inside the `if (params.viral)` block is just `= CH_final_contigs`.

Five independent classifiers run in parallel, none of their outputs consumed by anything downstream yet — `PARSE_GENOMAD`/`LOG_GENOMAD`, `PARSE_DEEPVIRFINDER_AND_VIRSORTER`, and the eggNOG-based `PROTEINS_VS_EGGNOG_5`/`EGGNOG_HITS_TO_CELL_OR_VIRUS`/`LOG_CELL_OR_VIRUS` triad that would summarize/combine them are all still commented out (end of `main.nf`, and in the `workflow {}` block respectively) pending further wiring. **None of these five processes had been exercised in a real (non-preview) run as of this writing** — verify a fresh run actually clears all five before treating this section as proven, not just the milestone documented under "Not wired into the stepwise-count system" above (that run predates this block's activation).

- **`GENOMAD_v1_11_1`**: `quay.io/biocontainers/genomad:1.11.1--pyhdfd78af_0` — confirmed to exist via the Quay API (it's the only `1.11.1` tag) and confirmed pullable/runnable on charlie via `singularity exec ... genomad --help` before adopting it. `params.DB_genomad_v1_11_1` points at a pre-built database directory, not downloaded by this pipeline.
- **`VIRSORTER_v2_2_3`** and **`CHECKV_v1_0_1`** were already containerized from before this integration (`jiarong/virsorter:latest`, `quay.io/biocontainers/checkv:1.0.1--pyhdfd78af_0`) — untouched here.
- **`DEEPVIRFINDER`**: no bioconda/biocontainers package exists for this tool, and upstream (`jessieren/DeepVirFinder`) ships no official container either — confirmed by checking both directly. Uses `replikation/deepvirfinder:latest`, a community image with traceable provenance (its Dockerfile lives in `replikation/What_the_Phage`, the peer-reviewed "What the Phage" metavirome pipeline) and confirmed working (`dvf.py --help`) before adopting it. Two things worth knowing if this ever needs revisiting: it's an unversioned `:latest` tag with no numbered releases since ~2019, so there's no way to pin a specific DeepVirFinder version the way the other tools here are pinned; and its bundled models live at `/DeepVirFinder/models` inside the image, not the tool's own default `./models`, so the script passes `-m /DeepVirFinder/models` explicitly rather than relying on the default.
- **`VIRALRECALL2`** is the one tool in this block still running the old way — `beforeScript`-activated host conda env (`/mnt/scgc/scgc_nfs/opt/common/anaconda3a/envs/viralrecall`), not a container. Not yet migrated.

### BWA_INDEX / BLAST_INDEX: self-bootstrapping reference

`params.contam_ref_fasta` defaults to `./reference/GRCh38_AG665_mm10.fa` — relative and gitignored, so a fresh clone has nothing there. Both `BWA_INDEX` and `BLAST_INDEX` are conditional: the workflow block checks for existing files next to `contam_ref_fasta` before deciding whether to run them, and `log.info` prints a one-time-cost notice right before either actually triggers.

- **`BWA_INDEX`** no longer runs `bwa index` locally — it downloads the fasta *and* the prebuilt `.amb/.ann/.bwt/.pac/.sa` from Zenodo (DOI `10.5281/zenodo.21682938`, "GORG Dark - Reference Contaminant Dataset") and verifies each against Zenodo's published MD5 before extracting. Several non-obvious things about this process, verified empirically (not documented anywhere) rather than assumed:
  - All 6 files served by that record are **zip archives**, each wrapping the real, already-decompressed file under its real name (fetching `<fasta>.ann.zip` returns a zip whose sole entry is literally `<fasta>.ann`) — extract with `unzip`, not `gunzip`.
  - Needs a real `curl` — BusyBox's `wget` (present in other biocontainers used elsewhere in this pipeline) cannot complete an HTTPS connection to zenodo.org at all.
  - **The container is `debian:bookworm-slim`, not a curl-specific image** (as of the Atrandi integration; a `curlimages/curl:8.21.0` version came before this and turned out to be a dead end — see below). curl/unzip aren't preinstalled on this image, so the script installs them itself first (`apt-get update -qq && apt-get install -y -qq curl unzip`), the same "install what a single existing image doesn't bundle" pattern `CONTAM_CONTIG_REMOVER` uses for `toolshed`/`interlap`. Runs as root by default, no custom entrypoint — neither `-u root` nor `--entrypoint ""` is needed here, unlike the old image.
  - **Why not `curlimages/curl` (its earlier container)**: that image is Alpine-based with no `/bin/bash` at all, which is fatal *regardless of this process's own `shell` directive* — verified directly by diffing `.command.run` across several successful tasks using entirely different images/containers: **Nextflow's Docker executor always launches the container's entrypoint as `/bin/bash -c "eval $(nxf_container_env); <configured-shell> -ue .command.sh"`**, for its own setup wrapper, regardless of what the process's `shell` directive says. `shell` only controls the *inner* invocation nested inside that wrapper, not the outer one — so a `shell '/bin/sh', '-ue'` directive (this process's earlier fix attempt) cannot work around an image that has no `/bin/bash` for the *outer* wrapper to exec in the first place; the container fails to even start (`exec: "/bin/bash": stat /bin/bash: no such file or directory`), before any script content runs. This only surfaces on a real (non-stub) run, since `-stub-run`'s CI coverage exercises the same container/wrapper mechanics with trivial `touch` content — the failure mode is identical either way, so if this ever regresses, stub-run should catch it too, not just real runs.
  - (Historical, from the `curlimages/curl` era, no longer applicable now that the container runs as root by default with bash present: that image ran as a non-root user, needing `-u root`; being Alpine's `/bin/sh` rather than bash, its `stub:` block's original brace-expansion (`touch ${fasta}{,.amb,.ann,...}`) silently produced one literal filename instead of six, since `sh` doesn't support that syntax — fixed by listing filenames explicitly, which is also just plainly clearer under bash.)
- **`BLAST_INDEX`** still builds locally via `makeblastdb`, now depends on `CH_bwa_fasta` (not a raw `file()` variable) so it properly waits on `BWA_INDEX`'s download when the fasta doesn't exist yet, rather than relying on script ordering alone.
- BWA readiness check: `<contam_ref_fasta>` itself exists *and* `.{amb,ann,bwt,pac,sa}` all exist (the fasta is no longer assumed to pre-exist, so this can't use `checkIfExists: true`).
- BLAST readiness check: more involved, because `makeblastdb` splits large references into numbered volumes and only writes a top-level `.nal` alias file — the workflow parses `.nal`'s `DBLIST` line and resolves each listed volume against `contam_ref_fasta`'s own directory (the entries are bare filenames), verifying the volume's `.nhr` actually exists rather than trusting the alias file's mere presence.
- Both index channels (`CH_bwa_fasta`/`CH_bwa_index`, `CH_blast_fasta`/`CH_blast_index`) are threaded as real process inputs into `CONTAM_READ_FINDER` and `CONTAM_CONTIG_FINDER` — this is what forces Nextflow to wait for a download/rebuild to finish before the step that needs it runs, not just process ordering in the script.
- Both processes have `cache false` and `publishDir ..., enabled: !workflow.stubRun`. The `enabled` guard is load-bearing, not defensive boilerplate — without it, `-stub-run`'s placeholder output gets copied into the real, shared reference directory (this happened once for real: 0-byte `.nhr`/`.nin`/`.nsq` files leaked into the reference dir from a stub run before the guard existed). `cache false` closes a related risk — it's not confirmed whether Nextflow's task hash distinguishes a `stub:` execution from a `script:` execution of the same process, so without it a stub run's cached result could in principle be reused by a later real `-resume` run, or vice versa.
- `CONTAM_READ_FINDER` and `CHECKM_v1_1_9` are the two steps that come close to Docker Desktop's memory ceiling locally. Rather than a hardcoded `memory` value tuned to one machine (which broke portability to CI's smaller runners), both use `memory { N.GB * task.attempt }` with `errorStrategy { task.exitStatus in [137, 140] ? 'retry' : 'terminate' }` and `maxRetries 3` — retries with more memory on an OOM kill instead of assuming a fixed ceiling, adapting to whatever's actually available (laptop, CI, HPC node). `CONTAM_READ_FINDER` starts at `5.GB` (its real historical OOM point against this reference); `CHECKM_v1_1_9` starts at `6.GB` (its `--reduced_tree` flag only guarantees "<16GB", covered across two attempts). `CONTAM_READ_FINDER` keeps `maxForks 1` so OOM-retries on one sample can't stack against another's concurrent attempt. **`CHECKM_v1_1_9`'s `maxForks 1` was removed** (2026-09) — on a real multi-capsule pool under the grid executor it serialized CheckM to one task at a time and, worse, stalled `PROKKA_v1_14_6`/`PROKKA_GFF_2_TSV` downstream (they're gated on `CH_translation_table`, derived from `CHECKM_v1_1_9.out`). At 6 GB/task the retry-stacking risk is minor; a laptop that needs the cap can add it back via a `withName` selector in its own (gitignored) `nextflow.config`.

### Stub-run support

16 of the pipeline's ~35 processes (`SAMPLE_READS`, `PHENIQS_DEMULTIPLEX`, `FASTQC_v0_11_9`, `TRIMMOMATIC_v0_32`, `COMPLEXITY_FILTER`, `KMERNORM_v1_0_0`, `BWA_INDEX`, `BLAST_INDEX`, `CONTAM_READ_FINDER`, `SPADES_v3_15_2`, `CONTAM_CONTIG_FINDER`, `CHECKM_v1_1_9`, `SSU_BLAST`, `SSU_GET_GENE`, `SSU_CLASSIFIER`, `GTDBTK_v2_0_0`) have a `stub:` block, covering every step that's either genuinely slow (SPAdes, CheckM, seqtk's/Pheniqs' full-pool passes, GTDB-Tk) or depends on a reference the CI runner doesn't have (bwa/blast alignment + indexing, SILVA for the SSU block, the ~66GB GTDB r207 DB). The rest — including 8 of the 10 Atrandi demultiplexing processes (see above), plus `PARSE_CLASSIFIER` and `PARSE_GTDBTK` (small pandas parsers that run for real against the stubbed upstream output) — are fast enough to just run for real even under `-stub-run`. Nextflow falls back to a process's normal `script:`/`shell:` when no `stub:` is defined, so partial coverage is safe.

The SSU-block stubs (`SSU_BLAST` → empty hit table, `SSU_CLASSIFIER` → empty outputs) are shaped so the two non-stubbed parsers after them still run: `SSU_GET_GENE` (pysam, real) gets an empty-but-valid BLAST6 file and produces an empty candidate fasta; `PARSE_CLASSIFIER` (real) reads the empty classification TSV and emits its three `…,0,<ID>` rows. `GTDBTK_v2_0_0` is doubly not-exercised for real in CI — its `script:` needs the 66GB DB, *and* the stub assembly is below `params.gtdbtk_min_bp` so the process is filtered out entirely — but its `stub:` still fabricates the two summary TSVs `PARSE_GTDBTK` reads, for the case where someone bumps the stub contig size.

Two things make the stubs more than placeholder `touch` calls:
- `TRIMMOMATIC_v0_32` → `COMPLEXITY_FILTER` → `KMERNORM_v1_0_0`'s stubs chain a **real subset** of actual read data (first 10 pairs) through each other, rather than empty files, because `DEINTERLEAVE` right after `KMERNORM_v1_0_0` is *not* stubbed and genuinely parses whatever it's given with `reformat.sh`.
- `CONTAM_CONTIG_FINDER`'s stub writes the same header line a real zero-hit run would produce, not an empty file, since `CONTAM_CONTIG_REMOVER` downstream isn't stubbed either and needs a properly-shaped TSV.

`ASSEMBLY_STATS_TABULATOR` prefixes every cell in its output with `STUB-RUN ` when `workflow.stubRun` is true, so stub output can never be mistaken for a real assembly's stats.

### Continuous integration

`.github/workflows/stub-run.yml` runs `nextflow run main.nf -stub-run --dev --indir .github/test_data -with-docker` on every push/PR, against tiny committed synthetic Atrandi-barcoded reads (`.github/test_data/ATRANDI_TEST_R{1,2}.fastq.gz`, produced by the committed `.github/test_data/generate_atrandi_test_data.py` — `input/` has real sample data but is intentionally untracked, so CI needs its own). The fixture embeds 3 barcode combos (10, 5, and 1 read pairs) so the real (non-stubbed) Atrandi demux logic gets exercised end-to-end: 2 capsules should survive `params.read_threshold`'s default of 3, and the 1-read combo should land in `undetermined`. Two things this workflow has to work around that a local run doesn't:
- `nextflow.config` is gitignored, so there's nothing in a fresh CI checkout to turn Docker on — `-with-docker` does that directly on the CLI instead.
- The real reference doesn't exist in CI either, so `BWA_INDEX`/`BLAST_INDEX` run in stub mode too (placeholder files, no real ~8GB Zenodo download) — this is exactly the case `-stub-run` was built for.

Several bugs fixed in the "self-bootstrapping reference" section above (`-u root`, the brace-expansion stub bug, from the `curlimages/curl` era) were only discovered because this workflow failed on real Linux — none of it surfaced in local macOS testing, since Docker Desktop's bind-mount layer is more lenient than real Linux Docker about exactly the kind of permission mismatch that bit `-u root`. If `BWA_INDEX`/`BLAST_INDEX` change again, treat a green run here as a floor, not sufficient proof by itself — the `/bin/bash`-in-container bug that replaced `curlimages/curl` with `debian:bookworm-slim` was the opposite case: `-stub-run` (locally and in CI) never exercises `BWA_INDEX`'s real `script:` block at all when the reference already appears to exist, and even when it does run, `-stub-run`'s CI fixture never triggers this path in the first place since it only ever runs with a stubbed reference — it only surfaced on a genuine full (non-stub) run against real data. `-stub-run` is a wiring smoke test, not proof that every `script:`/`shell:` block actually executes correctly against its real container.

### Stepwise count logging

Per-sample `.count`/TSV outputs from each stage are rolled up with `channel.collectFile(seed: COUNT_HEADER, storeDir: CH_stepwise_counts, cache: false)` directly in the workflow block — no separate `LOG_*` processes. `cache: false` is required on all of these: `collectFile`'s own cache is tied to `-resume` and keyed on input data, so a pure change to the aggregation logic with unchanged upstream data can silently reuse a stale result otherwise (this happened for real once). Output is `${params.output}/sample_tracking/stepwise_counts/{1..12}_<stage>.csv`, one file per stage including `9_checkm_completeness.csv` (built via a `.map()` that pulls the `Completeness` column out of CheckM's TSV directly in Groovy — no separate parsing process/container needed) and, from the 2026-09 annotation port, `10_prokka_stats.csv` (`PROKKA_GFF_2_TSV.out.countfile`), `11_ssu_classification.csv` (`PARSE_CLASSIFIER.out.countfile`), `12_gtdbtk_stats.csv` (`PARSE_GTDBTK.out`). Unlike stages 1–9 these carry non-numeric `Count` values (SSU/GTDB classification strings) — fine, the pivot is object-dtype and everything is stringified before write.

All per-stage channels then `.concat()` (not `.mix()`) into one `all_stepwise_counts.csv`, each file's own header line stripped before stacking so the combined file has exactly one. `.concat()` guarantees stage order regardless of which stage's tasks actually finish first; `.mix()` would interleave by completion order instead. `collectFile`'s default `sort` (`'hash'`) reorders entries by content hash regardless of input order, which was silently undoing the `.concat()` ordering — `sort: false` ("append as produced") is required alongside it.

Finally, `ASSEMBLY_STATS_TABULATOR` reads `all_stepwise_counts.csv` and pivots it (long → wide) into `${params.output}/assembly_stats.csv`, one row per sample, columns in a fixed order (`LIST_col_order`). Handles the `Contam_filtered_readcount == "NO_CHANGE"` case (when `CONTAM_READ_REMOVER` found nothing to remove) by copying `Normalized_readcount` in as the numeric value.

### `kmernorm`'s licensing gap: no container, user-provided binary required

The `kmernorm` binary (Mingkun Li) has no license anywhere — not on its SourceForge page, not in its source archive — meaning it's technically all-rights-reserved by default copyright. `KMERNORM_v1_0_0` used to depend on a third-party Docker image wrapping that same unlicensed source, with no public Dockerfile or build provenance.

The process no longer references any container — it declares `container null`, so it always runs directly against a `kmernorm` binary on the host PATH, which the user must build and provide themselves. Installing and running it is the user's own responsibility (see `README.md` and `THIRD_PARTY_LICENSES.md`), not something this pipeline warrants or vouches for.

`container null` on a process overrides any global `process.container`/`docker.enabled` default from `nextflow.config`, which is what makes this reliable regardless of what the user's own gitignored `nextflow.config` sets. (An earlier iteration tried to get this same effect via an opt-in config setting `docker.enabled = false` inside a `withName` block — that's not a valid per-process directive; Nextflow warns `Unknown directive 'docker' for process 'KMERNORM_v1_0_0'` and silently ignores it, so the process kept running in the Docker image despite the opt-in being "on". `container = null`, set directly on the process, is the documented mechanism that actually works, which is why it's now the hardcoded default rather than an opt-in `conf/` file.)

### Retiring the shared kmernorm image as a general-purpose container

That third-party image used to be reused as a generic Python/bash container by six unrelated steps (`COMPLEXITY_FILTER`, `CONTAM_READ_REMOVER`, `TRIM_CONTIGS`, `MEASURE_SAG`, `CONTAM_CONTIG_REMOVER`, `ASSEMBLY_STATS_TABULATOR`) — none of it for k-mer normalization, just because it happened to have Python + the right libraries. Given the licensing gap above, each was moved to a real, versioned `quay.io/biocontainers` image instead, based on what the underlying script actually imports:

- **`six`, everywhere it appeared, was simply dead weight** — every usage (`templates/complexity_filter.py`, `templates/contam_read_remover.py`, `templates/contam_contig_remover.py`) was a Python 2/3 shim with a direct stdlib equivalent (`six.string_types` → `str`, `six.moves.zip_longest` → `itertools.zip_longest`, `six.iteritems(d)` → `d.items()`). Removing it dropped a dependency with no standalone biocontainers image and didn't change behavior.
- **`CONTAM_READ_REMOVER`** and **`COMPLEXITY_FILTER`** → `quay.io/biocontainers/pysam:0.24.0--py312hf5ad864_1` (pysam is their only real dependency once `six` is gone). `COMPLEXITY_FILTER`'s `templates/complexity_filter.py` also had its own `parmap` dependency — its one call site (`multiprocess()`'s inner loop) was rewritten from `parmap.map(f, g, *args, **kwargs)` to `pool.starmap(f, [(item,) + args for item in g])` against the `multiprocessing.Pool` the script already creates, which is behaviorally identical (verified locally: same output, order-preserving) and needs no extra package at all.
- **`TRIM_CONTIGS`** and **`MEASURE_SAG`** → `quay.io/biocontainers/biopython:1.84` (Biopython-only).
- **`ASSEMBLY_STATS_TABULATOR`** → `quay.io/biocontainers/pandas:2.2.1` (numpy comes bundled).
- **`CONTAM_CONTIG_REMOVER`** needs Biopython + `toolshed` + `interlap` (real interval-overlap logic in `overlap_distance()`, not a removal candidate). No public image bundles all three, so it uses the `biopython:1.84` image plus `beforeScript 'pip install --quiet toolshed==0.4.8 interlap==0.2.7'` — both are small, pure-Python packages with no compiled extensions, so this doesn't need a build toolchain, just network access at task start. Versions are pinned (both packages' current PyPI latest, and the exact versions this was verified against) rather than left floating, so a new release can't silently change behavior underneath this process. This is still an existing public image, not a custom one built/published for this pipeline — but note it does mean this one process needs internet access from inside its container on every run, unlike the others.

`KMERNORM_v1_0_0` itself never used a `quay.io/biocontainers` replacement — it's the one process that actually needs the `kmernorm` tool itself, not a generic Python/bash environment, and is handled via the user-provided-binary approach above (`container null`), not a container swap.

## Known gaps / quirks

- `params.reference_threshold` (bwa `aln -n`) and `params.contam_min_length`/`contam_min_percid` (blast filtering thresholds) are declared but not all necessarily enforced in the same process that declares related params — check each `template_*.py`/shell block directly rather than assuming from the param's declared location.
- `docker.autoMounts` in `nextflow.config` triggers an "Unrecognized config option" warning on the Nextflow version currently in use (harmless).
- **`params.prokka` was declared twice** (once near the top under `//# VIRAL` pointing at the real reference, `/mnt/scgc_nfs/ref/uniprot_swissprot_prokka.fasta`; again lower down under a since-removed `//#. ANNOTATION` header, pointing at `./annot_database/uniprot_swissprot_prokka.fasta`). Nextflow params are last-assignment-wins, so the second, relative-path declaration silently overrode the first — and that relative path resolved to a 134-byte **Git LFS pointer file** (`git lfs` was never run on charlie to materialize it), not the real ~134MB SwissProt database. `PROKKA_v1_14_6`'s `--proteins` flag was therefore pointed at a non-FASTA stub for every run to date, including the 2026-08-19 confirmed end-to-end milestone — Prokka doesn't hard-fail on a malformed `--proteins` file, it just gets none of the intended trusted-protein hints, so this degraded annotation quality silently rather than crashing anything. Fixed by removing the second declaration; if annotation quality on prior runs' output matters, they'll need re-running (this param's value flows into `PROKKA_v1_14_6`'s script text, so a `-resume` will correctly detect the change and re-run it and everything downstream).
